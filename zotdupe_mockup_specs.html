ZotDupe — Semantic Duplicate Checker
Detectare duplicate semantice cross-type in biblioteca Zotero. Gaseste aceeasi sursa salvata ca tipuri diferite de item (webpage vs statute vs book), cu titluri diferite, metadate diferite, formatari diferite — si propune merge inteligent cu alegerea item-ului canonical.
🎯
Problema pe care o rezolvam
De ce detectorul nativ Zotero si Zoplicate nu sunt suficiente

Detectia nativa Zotero (si Zoplicate)

Zotero foloseste doar DOI, ISBN si titlu exact + an + autori. Zoplicate adauga non-duplicate marking si bulk merge, dar nu schimba algoritmul de detectie. Ambele detecteaza doar duplicate „triviale".

De asemenea, Zotero nu permite merge intre tipuri diferite de item (issue #1393, deschis din 2017). Daca ai aceeasi lege salvata ca statute si ca webpage, Zotero nu le vede ca duplicate si nici nu permite merge-ul lor manual.

Tipuri de duplicate semantice (invizibile pentru Zotero)

A
Cross-type duplicates: Aceeasi sursa, tipuri diferite. Ex: Legea 104/2003 ca statute, webpage, legal_case sau report.
B
Title variation duplicates: Acelasi articol cu titluri diferite. Ex: „GDPR and biobank consent" vs „Regulation 2016/679 implications for biobank research: consent models" vs „GDPR implications for biobank research".
C
Edition/version duplicates: Editii diferite ale aceleiasi carti: „Principles of Biomedical Ethics, 7th ed." vs „Principles of Biomedical Ethics, 8th ed." — care e un duplicat real vs o editie nou-citabila.
D
Preprint → journal duplicates: ArXiv preprint + articol publicat in jurnal, cu DOI-uri diferite si titluri usor diferite.
E
Translation duplicates: Articol in engleza si traducere in romana, sau lege romaneasca cu titlu oficial si titlu tradus in engleza.
F
Legislation duplicates: Aceeasi lege cu referinte la Monitorul Oficial, la legislatie.just.ro, la forma consolidata, la varianta initiala. Tipuri variate: statute, bill, webpage, document.

Algoritmul de detectie multi-strat
7 nivele de matching cu scoruri de confidenta ponderate

Algoritmul combina mai multe semnale intr-un scor de similaritate compozit (0.0 — 1.0). Fiecare strat contribuie un scor partial, ponderat dupa fiabilitate. Doar perechile cu scor > threshold (configurabil, default 0.65) sunt raportate.

Strat 1 — Identificator exact (pondere: definitiva)

Daca doua item-uri au acelasi DOI, PMID, PMCID sau ISBN → scor = 1.0, duplicate cert. Normalizare: lowercase, fara prefix „doi:", fara trailing slashes, ISBN fara cratime.

Strat 2 — Titlu normalizat + an (pondere: 0.35)

Normalizare titlu: lowercase → remove diacritice → remove punctuatie → collapse whitespace → remove articles (the, a, an, der, die, das) → remove stop words comune. Comparatie: Levenshtein ratio ≥ 0.85 SAU Jaccard similarity pe bigrame ≥ 0.75. Bonus +0.10 daca anul este identic (±1 an).

Strat 3 — Autori (pondere: 0.20)

Extrage lastName al fiecarui autor. Compara seturile de autori cu Jaccard similarity. Scor partial = Jaccard(autori_A, autori_B). Tratare speciala: entitati institutionale (ex: „Parlamentul Romaniei", „European Commission") — match exact pe text normalizat.

Strat 4 — Fingerprint legislativ (pondere: 0.30, doar pentru tipuri juridice)

Extrage din titlu si din campuri un „fingerprint legislativ":

Regex: /(legea?|oug|hg|og|ordin|directiva?|regulament|decizie?)\s*(nr\.?\s*)?\d+[\/\-]\d{2,4}/i
Exemplu: "Legea nr. 104/2003" → fingerprint = "L_104_2003"
         "Law 104/2003"       → fingerprint = "L_104_2003"
         "L. 104/2003 M.Of."  → fingerprint = "L_104_2003"

Daca doua item-uri au acelasi fingerprint legislativ → scor_legislativ = 0.95. Se aplica si pe legislatie europeana: Directive 2013/48/EU, Regulation (EU) 2016/679.

Strat 5 — URL / acces (pondere: 0.10)

Daca doua item-uri au URL-uri pe acelasi domeniu (ex: ambele pe legislatie.just.ro) si se refera la acelasi act → bonus similaritate. Daca un item e webpage si celalalt statute, dar URL-ul contine ID-ul actului → confirmare.

Strat 6 — Preprint ↔ Journal (pondere: bonus 0.15)

Daca un item e de tip preprint sau are DOI ArXiv/bioRxiv/medRxiv, si celalalt e journalArticle, si titlurile au Levenshtein ≥ 0.80 si cel putin un autor comun → se adauga bonus 0.15 la scor.

Strat 7 — Traduceri (pondere: context)

Daca titlurile sunt in limbi diferite (detectat cu heuristica: prezenta diacriticelor romanesti, cuvinte cheie de limba) si autorii sunt identici si anul este identic → scor = 0.75 cu tag „posibila traducere". Utilizatorul decide daca le merge sau le lasa separate.

Scor final compozit

scor = max(
  scor_identificator,                              // Strat 1 (definitiv daca = 1.0)
  W_titlu * scor_titlu                             // Strat 2
  + W_autori * scor_autori                         // Strat 3
  + W_legislativ * scor_legislativ                 // Strat 4
  + W_url * scor_url                               // Strat 5
  + bonus_preprint                                 // Strat 6
)
// W_titlu=0.35, W_autori=0.20, W_legislativ=0.30, W_url=0.10
// Normalizat la [0, 1]

Clasificare confidenta

  • ≥ 0.90 — Very High — Propunere auto-merge (cu confirmare)
  • 0.75 — 0.89 — High — Probabil duplicat, necesita confirmare
  • 0.65 — 0.74 — Medium — Posibil duplicat, revizuire manuala
  • Sub 0.65 — Nu este raportat (configurabil)

Structuri de date si performanta
Indexare si comparatii optime pentru biblioteci mari

Indexare la startup (o singura trecere)

interface NormalizedItem {
  id: number;                    // Zotero item ID
  key: string;                   // Zotero item key
  itemType: string;              // "journalArticle", "statute", "webpage", etc.
  titleNorm: string;             // titlu normalizat (lowercase, fara diacritice/punctuatie)
  titleBigrams: Set<string>;     // set de bigrame pentru Jaccard
  authorLastNames: Set<string>;  // set de nume de familie normalizate
  year: number | null;
  doi: string | null;            // normalizat
  pmid: string | null;
  isbn: string | null;
  url: string | null;
  urlDomain: string | null;
  legalFingerprint: string|null; // ex: "L_104_2003", "DIR_2013_48_EU"
  collections: string[];         // IDs de colectii
  tags: string[];
  dateAdded: string;
  attachmentCount: number;
  noteCount: number;
}

interface DuplicateCluster {
  id: string;                    // cluster ID unic
  items: NormalizedItem[];       // 2+ item-uri in cluster
  canonicalId: number | null;    // item ales ca master
  score: number;                 // scor de similaritate maxim in cluster
  confidence: "very_high" | "high" | "medium";
  reasons: string[];             // ex: ["DOI exact match", "Cross-type: statute ↔ webpage"]
  matchDetails: {
    layer: number;               // stratul care a produs match-ul
    titleSim: number;
    authorSim: number;
    legalMatch: boolean;
    urlMatch: boolean;
    crossType: boolean;
    preprint: boolean;
  };
  status: "pending" | "merged" | "not_duplicate" | "skipped";
}

Strategie de comparatie (evitarea O(n²))

Pentru o biblioteca de N item-uri, comparatia naiva este O(N²). Cu N=20.000, asta inseamna 200M de comparatii — prea lent. Solutia:

1
Blocking prin identificatori: Construieste hashmap-uri pe DOI, PMID, ISBN. Orice coliziune = pereche candidata. Complexitate: O(N).
2
Blocking prin fingerprint legislativ: Hashmap pe fingerprint-uri. Orice coliziune = pereche candidata. O(N).
3
Blocking prin Year + FirstAuthor: Grupeaza item-urile dupa (an, primul autor). Compara doar in cadrul fiecarui grup. Reduce dramatic numarul de perechi.
4
MinHash LSH pe bigrame de titlu: Locality-Sensitive Hashing cu 128 de hash-uri si 8 bande. Gaseste rapid perechi cu Jaccard estimat ≥ 0.5 pe titlu. Complexitate: ~O(N).
5
Scoring complet: Doar pe perechile candidate din pasii 1-4. Aplica toate cele 7 straturi. Filtreaza sub threshold.

Performanta estimata: Biblioteca de 20.000 item-uri: indexare ~2s, comparatii ~3-5s, total < 8s.

Logica de merge cross-type
Cum se alege itemul canonical si cum se combina metadatele

Selectia automata a item-ului canonical

Plugin-ul propune un item „master" pe baza unui scor de calitate:

qualityScore(item) = 
    (item.doi ? 20 : 0)
  + (item.isbn ? 15 : 0)
  + (item.pmid ? 15 : 0)
  + (item.abstract ? 10 : 0)
  + (item.url ? 5 : 0)
  + (item.attachmentCount * 5)    // PDF-uri atasate
  + (item.noteCount * 3)          // note
  + (item.collections.length * 2) // apartine la colectii
  + (item.tags.length * 1)        // tag-uri
  + typeBonus(item.itemType)      // bonus pentru tipuri "corecte"
  + (item.dateAdded < other.dateAdded ? 5 : 0)  // item-ul mai vechi

typeBonus() acorda punctaj preferential tipurilor mai specifice:

  • journalArticle: +10, book: +10, statute: +10
  • conferencePaper: +8, thesis: +8, report: +6
  • preprint: +4, webpage: +2, document: +1

Utilizatorul poate schimba item-ul canonical cu un click.

Combinarea metadatelor la merge

Reguli per camp:

  • Type: Se pastreaza tipul canonical (utilizatorul poate schimba)
  • Title: Se pastreaza cel mai complet (cel mai lung, cu diacritice)
  • DOI/PMID/ISBN: Se pastreaza orice identificator non-null
  • Abstract: Se pastreaza cel mai lung
  • URL: Se pastreaza (daca canonical nu are URL dar sursa da)
  • Collections: UNION — item-ul rezultat apartine tuturor colectiilor
  • Tags: UNION — toate tag-urile se pastreaza
  • Notes: Se muta toate notele la item-ul canonical
  • Attachments: Se muta toate PDF-urile la canonical. Daca exista PDF-uri identice (hash), se pastreaza unul singur
  • Related: UNION — relatiile se combina
  • Extra: Se concateneaza daca ambele au continut

Fiecare camp cu valori diferite este afisat in UI cu optiunea de a alege sursa.

Tratarea merge cross-type (workaround Zotero)

Deoarece Zotero nativ nu permite merge intre tipuri diferite (issue #1393):

1
Se schimba tipul item-urilor non-canonice la tipul canonical (via Zotero.Item.setType())
2
Se face merge-ul standard Zotero (pastreaza colectii, tag-uri, atasamente, citari)
3
Citarile din documente Word se actualizeaza automat (Zotero face asta nativ la merge)

Plan de dezvoltare, limitari si integrari
Estimari de efort, faze de implementare, edge cases

Faze de implementare

F1
MVP (3-4 saptamani): Indexare + blocking DOI/ISBN + titlu fuzzy + UI de baza (lista clustere + merge simplu). Doar same-type merge.
F2
Cross-type + legislatie (2-3 saptamani): Fingerprint legislativ + cross-type merge workaround + preprint→jurnal + MinHash LSH.
F3
UI complet + optiuni avansate (2 saptamani): Merge preview + field picker + traduceri + export raport + integrare Zoplicate (non-dup pairs).
F4
Optimizare + testare (2 saptamani): Benchmark pe biblioteci reale 5k/20k/50k. Tuning threshold-uri. Edge cases. Packaging XPI + documentatie.

Efort total estimat: 35-45 zile-om

Limitari cunoscute

  • Nu inlocuieste judecata umana: Editiile diferite (7th vs 8th) NU trebuie merge-uite. Plugin-ul semnaleaza dar utilizatorul decide.
  • MinHash LSH are false negatives: ~5-10% din perechi cu Jaccard real > 0.5 pot fi ratate. Acceptabil, deoarece blocking-ul pe ID-uri le prinde pe cele importante.
  • Cross-type merge pierde campuri specifice tipului: Daca merge statute → webpage, campurile specifice statute (codeNumber, session) se pierd daca target-ul e webpage. Solutie: mereu merge catre tipul mai specific.
  • Traduceri sunt dificil de detectat automat: Fara un API de traducere, detectia se bazeaza pe heuristici (limba detectata din caractere + autori identici). False positive rate mai mare.
  • Zotero nu are API public de „merge": Merge-ul se face prin metode interne Zotero (Zotero.Items.merge()), care pot evolua intre versiuni.

Compatibilitate

  • Zotero 7+ (obligatoriu, utilizeaza API-ul modern)
  • Zoplicate: Compatibil — respecta perechile non-duplicate marcate. Poate importa lista de non-duplicates de la Zoplicate si invers.
  • PP2Zotero: Poate fi invocat automat dupa conversia Paperpile → Zotero, pentru a detecta duplicatele create la import.

Integrare cu PP2Zotero (hook optional)

Dupa o conversie PP2Zotero, item-urile importate din DOI pot fi duplicate cu item-uri existente. ZotDupe poate rula automat o scanare limitata doar pe item-urile nou-importate, oferind merge instant.
